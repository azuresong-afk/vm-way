# Установка, обновление и резервное копирование

«Устранение» поставляется как стек Docker Compose из трёх сервисов:

| Сервис | Что это | Порт хоста |
|---|---|---|
| `web` | nginx без root: отдаёт интерфейс и проксирует `/api/*` на `app` (префикс отрезается, один origin, без CORS), строгий CSP | `VM_WEB_PORT`, по умолчанию **18081**, на всех интерфейсах (`VM_WEB_BIND`), **по HTTP** — для работы нужен TLS, см. [раздел 5](#5-https-для-веб-интерфейса) |
| `app` | API (FastAPI) и фоновые задачи: импорт прогонов, опрос источников, повторные проверки | `VM_API_PORT`, по умолчанию 18001, только `127.0.0.1` |
| `db` | PostgreSQL 16, данные в томе `vm_pg_data` | `VM_DB_PORT`, по умолчанию 15433, только `127.0.0.1` |

Порты по умолчанию взяты из контракта «Платформы» и не пересекаются со «Сканером» (18080 / 18000 / 15432) и «Аттестацией» (18082 / 18002 / 15434), поэтому продукты можно ставить на одну машину.

## 1. Требования

- Linux-сервер x86-64 (подойдёт и ARM: образы собираются из исходников на месте), 2 ядра, 2 ГБ памяти, 5 ГБ на диске.
- Docker Engine 24+ и Docker Compose v2 (`docker compose version`).
- `openssl` — для `scripts/gen-env.sh`; `curl` и `python3` — для `scripts/smoke.sh` (необязательно).
- Сетевой доступ от сервера к API «Сканера» (обычно его веб-интерфейс, `https://…/api`).
- Для сборки образов нужен доступ к Docker Hub, PyPI и npm. В закрытом контуре соберите образы снаружи и перенесите (`docker save` / `docker load`, см. раздел 8).

## 2. Настройка `.env`

Все настройки — в файле `.env` в корне репозитория. Шаблон со всеми переменными и комментариями — `.env.example`.

Быстрый путь — сгенерировать `.env` со случайными секретами:

```bash
scripts/gen-env.sh
```

Скрипт копирует `.env.example`, заполняет `VM_SECRET_KEY`, `VM_ENCRYPTION_KEY`, `POSTGRES_PASSWORD` и `VM_ADMIN_PASSWORD` и печатает пароль администратора. Существующий `.env` он не трогает. Права на файл — `600`.

Вручную: `cp .env.example .env` и замените все `CHANGE_ME`:

| Переменная | Что указать |
|---|---|
| `VM_SECRET_KEY` | Ключ подписи токенов, не короче 32 символов: `python3 -c "import secrets; print(secrets.token_urlsafe(48))"` |
| `VM_ENCRYPTION_KEY` | Ключ шифрования паролей источников и SSH-учёток хостов, 32 байта в base64: `python3 -c "import os, base64; print(base64.b64encode(os.urandom(32)).decode())"` |
| `POSTGRES_PASSWORD` | Пароль БД, только буквы и цифры (подставляется в адрес подключения) |
| `VM_ADMIN_USERNAME`, `VM_ADMIN_PASSWORD` | Первый администратор, пароль не короче 10 символов. Создаётся при старте, только если пользователей ещё нет |
| `VM_SCANNER_WEB_URL` | Адрес веб-интерфейса «Сканера» для ссылок «Открыть в Сканере» (необязательно) |
| `VM_WEB_PORT`, `VM_API_PORT`, `VM_DB_PORT` | Порты хоста, если значения по умолчанию заняты |
| `VM_WEB_BIND`, `VM_TRUSTED_PROXY` | Адрес, на котором слушает веб, и адрес обратного прокси с TLS — см. [раздел 5](#5-https-для-веб-интерфейса) |

Перед запуском API контейнер `app` проверяет настройки (`python -m app.preflight`). Пустые, шаблонные (`CHANGE_ME`) или слабые секреты останавливают старт, а причина видна в `docker compose logs app`.

> **Сохраните `.env` отдельно от резервных копий.** `VM_ENCRYPTION_KEY` нужен, чтобы расшифровать пароли сервисных учёток «Сканера». Без него копия базы восстановится, но пароли источников придётся ввести заново.

## 3. Запуск

```bash
docker compose up --build -d
docker compose ps          # app, web и db — healthy
```

Первый запуск собирает образы (несколько минут). При старте `app` по порядку:

1. проверяет секреты;
2. ждёт базу и применяет миграции (`alembic upgrade head`, до `VM_DB_WAIT_ATTEMPTS` попыток по 2 с);
3. создаёт первого администратора из `.env`, если пользователей нет;
4. запускает API в одном процессе: фоновые задачи работают пулом потоков внутри него.

`app` считается готовым (`healthy`), когда `/health/ready` отвечает 200: база доступна и схема на последней миграции. `web` стартует только после этого.

Проверка всего стека одной командой:

```bash
scripts/smoke.sh           # nginx, заголовки безопасности, готовность API, вход администратора
```

Логи: `docker compose logs -f app`. У всех сервисов включена ротация логов (5 файлов по 20 МБ). Сервисы поднимаются сами после перезагрузки сервера (`restart: unless-stopped`).

Остановка: `docker compose down` (данные в томе `vm_pg_data` сохраняются). `docker compose down -v` **удаляет базу**.

## 4. Первый вход

Откройте `http://СЕРВЕР:18081` и войдите администратором из `.env`. По HTTP работайте только на стенде: перед тем как заводить пользователей и вводить пароли и ключи хостов, включите HTTPS ([раздел 5](#5-https-для-веб-интерфейса)).

Администратор управляет пользователями, проектами, источниками и видит журнал аудита, но рабочих операций с заявками не выполняет (разделение обязанностей). Поэтому сразу заведите пользователей в «Администрирование → Пользователи и роли»:

- **Руководитель** — видит всё, назначает и переводит заявки, импортирует прогоны, запускает проверки;
- **Исполнитель** — берёт заявки, ведёт их, запускает повторную проверку;
- **Наблюдатель** — только просмотр (например, представитель заказчика).

## 5. HTTPS для веб-интерфейса

Сам стек отдаёт веб-интерфейс по HTTP. Через него идут пароли пользователей, токены доступа, пароль сервисной учётки «Сканера» и закрытые ключи SSH для хостов заказчика, поэтому на рабочей установке перед `web` обязательно ставится обратный прокси с TLS, а прямой доступ к порту 18081 закрывается. Сертификат выпускается так же, как для остальных внутренних сервисов (корпоративный УЦ или ACME).

### Прокси на том же сервере

1. В `.env` оставьте веб только на localhost и разрешите ему верить заголовку прокси с адресом клиента:

   ```bash
   VM_WEB_BIND=127.0.0.1
   VM_TRUSTED_PROXY=172.16.0.0/12
   ```

   `VM_TRUSTED_PROXY` — адрес, с которого запросы прокси приходят в контейнер `web`. Для прокси на том же сервере это шлюз сети Docker; подсеть `172.16.0.0/12` покрывает сети Docker по умолчанию. Точный адрес: `docker network inspect vm-way_default --format '{{(index .IPAM.Config 0).Gateway}}'` (имя сети — по каталогу установки). Без этой настройки в журнале аудита вместо адресов пользователей будет адрес прокси.

2. Примените: `docker compose up -d`.

3. Настройте прокси. Пример для nginx на хосте (`/etc/nginx/conf.d/vm.conf`):

   ```nginx
   server {
       listen 80;
       server_name vm.example.ru;
       return 301 https://$host$request_uri;
   }

   server {
       listen 443 ssl;
       http2 on;
       server_name vm.example.ru;

       ssl_certificate     /etc/nginx/tls/vm.example.ru.crt;   # сертификат с цепочкой
       ssl_certificate_key /etc/nginx/tls/vm.example.ru.key;
       ssl_protocols TLSv1.2 TLSv1.3;
       add_header Strict-Transport-Security "max-age=31536000" always;

       location / {
           proxy_pass http://127.0.0.1:18081;
           proxy_set_header Host $host;
           # Адрес клиента для журнала аудита. Именно так, без $proxy_add_x_forwarded_for:
           # иначе клиент сможет подставить адрес своим заголовком.
           proxy_set_header X-Forwarded-For $remote_addr;
           proxy_set_header X-Forwarded-Proto https;
           proxy_read_timeout 300s;   # выгрузка журнала аудита за большой период
       }
   }
   ```

   То же для Caddy (сертификат он получит и продлит сам, если сервер доступен для ACME):

   ```
   vm.example.ru {
       reverse_proxy 127.0.0.1:18081
   }
   ```

   Остальные заголовки безопасности (CSP, `X-Frame-Options` и другие) ставит сам `web`, дублировать их в прокси не нужно.

4. Проверьте: `scripts/smoke.sh https://vm.example.ru`, затем войдите и убедитесь, что в «Журнале аудита» у входа стоит ваш адрес, а не адрес прокси. Снаружи `http://СЕРВЕР:18081` открываться больше не должен.

### Общий балансировщик или прокси на другом сервере

Оставьте `VM_WEB_BIND=0.0.0.0`, в `VM_TRUSTED_PROXY` укажите адрес балансировщика, а порт 18081 закройте межсетевым экраном для всех, кроме него. Учтите, что правила Docker обходят `ufw`: ограничение ставьте в цепочке `DOCKER-USER` или на сетевом оборудовании. Участок от балансировщика до сервера при этом идёт по HTTP — он должен быть в доверенном сегменте.

### Что ещё закрыто

- Описание API (`/api/docs`, `/api/openapi.json`) отдаётся только на демо-стенде (`VM_DEMO=1`): оно доступно без входа, и на рабочей установке отвечает 404.
- API (`VM_API_PORT`) и база (`VM_DB_PORT`) слушают только `127.0.0.1` сервера, наружу их открывать не нужно.

## 6. Подключение «Сканера»

1. В «Сканере» создайте сервисную учётную запись. Для импорта достаточно роли **auditor**; для повторной проверки (прицельный прогон по учётным записям хостов) нужна роль **operator** и право `host_credentials`. Дайте ей доступ к договору, с которым будет работать «Устранение».
2. В «Устранении»: «Администрирование → Проекты» — создайте проект (заказчик, договор).
3. «Администрирование → Источники» → «Добавить»:
   - **Адрес API** — API «Сканера» через его веб-интерфейс, например `https://scanner.example.ru/api` (или `http://СЕРВЕР:18080/api`). Порт API «Сканера» 18000 слушает только localhost его сервера, поэтому снаружи нужен адрес веба с `/api`;
   - **Адрес веб-интерфейса** — для ссылок «Открыть в «Сканере»»;
   - **Учётная запись** и **Пароль** — сервисная учётка из п. 1. Пароль хранится зашифрованным (AES-GCM) и в интерфейс не возвращается;
   - **Опрос, минут** (по умолчанию 15) и **Импортировать новые прогоны автоматически**;
   - **Проверять сертификат TLS** — выключайте только на стенде с самоподписанным сертификатом.
4. Откройте источник: «Проверить связь», затем «Привязать» договор «Сканера» к проекту «Устранения».
5. Импорт: опрос сам подтянет завершённые прогоны, а руководитель может нажать «Импортировать новые прогоны» на «Сводке». Повторный импорт не создаёт дублей.

## 7. Демо-стенд

Демо показывает весь цикл без настоящего «Сканера»: проект «Демо: АО «Северный порт»», встроенный мок «Сканера» (`mock://demo`: Debian 12, Astra Linux SE 1.7, РЕД ОС 7.3, 20 хостов, три плановых прогона) и пользователей `manager`, `ciso`, `engineer`, `engineer2`, `viewer`.

```bash
scripts/gen-env.sh --demo   # VM_DEMO=1 и случайный VM_DEMO_PASSWORD
docker compose up --build -d
```

Демо-прогоны импортируются в первые секунды после старта. Пошаговая проверка на демо-стенде — [TESTING.md](TESTING.md). Демо-режим — только для стенда: на установке у заказчика держите `VM_DEMO=0`.

## 8. Обновление

```bash
scripts/backup.sh                 # сначала копия
git pull
docker compose up --build -d      # пересборка образов; миграции применятся при старте app
docker compose ps                 # app — healthy
```

При первом старте после обновления пароли источников «Сканера», сохранённые прежними версиями, перешифровываются с привязкой к своей записи (в логе `app`: «Пароли источников привязаны к своим записям»); прежняя версия кода их после этого не прочитает.

Миграции только добавляются, откат версии назад не поддерживается: чтобы вернуться, восстановите копию, сделанную до обновления, на прежней версии кода.

**Закрытый контур.** Соберите образы на машине с доступом в интернет и перенесите:

```bash
docker compose build
docker save vm-ustranenie-app:local vm-ustranenie-web:local postgres:16 | gzip > vm-images.tar.gz
# на целевом сервере, в каталоге с кодом той же версии и .env:
docker load < vm-images.tar.gz
docker compose up -d --no-build
```

Тег образов задаётся `VM_IMAGE_TAG` (по умолчанию `local`).

## 9. Резервное копирование и восстановление

**Копия** (стек запущен, работу останавливать не нужно — `pg_dump` снимает согласованный снимок):

```bash
scripts/backup.sh                       # в ./backups/ГГГГ-ММ-ДД_ЧЧММСС
scripts/backup.sh /mnt/backup/vm-$(date +%F)
```

В каталоге копии: `db.dump` (формат custom), `manifest.txt` (время, версия схемы, коммит) и `SHA256SUMS`. Скрипт проверяет, что дамп читается. `.env` в копию не входит — храните его отдельно.

Ежедневная копия через cron:

```cron
30 2 * * * cd /opt/vm-way && scripts/backup.sh >> /var/log/vm-backup.log 2>&1
```

**Восстановление** заменяет текущую базу, поэтому требует `--yes`:

```bash
scripts/restore.sh backups/2026-11-04_023000 --yes
```

Скрипт проверяет контрольную сумму, останавливает `app` и `web`, пересоздаёт базу, загружает дамп и запускает сервисы. Если копия сделана на более старой версии, недостающие миграции применятся при старте `app`. В `.env` должен быть тот же `VM_ENCRYPTION_KEY`, что и при создании копии. Журнал аудита восстанавливается целиком, защита от изменения записей (триггер) сохраняется.

**На другой сервер:** скопируйте код той же версии, `.env` и каталог копии, выполните `docker compose up --build -d`, затем `scripts/restore.sh КАТАЛОГ --yes`.

## 10. Если что-то не работает

| Признак | Что проверить |
|---|---|
| `app` перезапускается, в логе `[preflight] ОШИБКА` | Исправьте названную переменную в `.env`, затем `docker compose up -d` |
| `app` пишет «миграции не применены за N попыток» | База недоступна или `POSTGRES_PASSWORD` не совпадает с тем, с которым создан том `vm_pg_data`. Пароль БД меняется только вместе с томом (или через `ALTER USER` в самой базе) |
| `docker compose` ругается «задайте POSTGRES_PASSWORD» | Нет `.env` или в нём нет `POSTGRES_PASSWORD` — выполните `scripts/gen-env.sh` |
| В журнале аудита у всех один и тот же адрес | Запросы идут через обратный прокси, а `VM_TRUSTED_PROXY` не задан или не совпадает с адресом, с которого прокси приходит в контейнер `web` — см. [раздел 5](#5-https-для-веб-интерфейса) |
| `/api/docs` отвечает 404 | Так и задумано вне демо-режима (`VM_DEMO=1`). Для разработки запустите API с `VM_DEMO=1` |
| `Bind for 0.0.0.0:18081 failed: port is already allocated` | Порт занят — задайте другой `VM_WEB_PORT` (или `VM_API_PORT`, `VM_DB_PORT`) в `.env` |
| Вход администратора не работает | Администратор создаётся только при пустой базе. Свой пароль он меняет сам (значок ключа в карточке пользователя в меню); забытый сбрасывает другой администратор в «Пользователях» или восстановление копии |
| «Слишком много неудачных попыток. Повторите через N мин.» | Сработала защита от перебора пароля: 5 неудачных входов за 15 минут с одного адреса в одну учётную запись (ещё есть пределы на адрес и на учётную запись, см. `VM_LOGIN_*` в `.env.example`). Блокировка снимается сама; срочно — удалите строки из таблицы `login_failures`. В журнале аудита — `auth.lockout` |
| «Проверить связь» у источника — ошибка TLS | Сертификат «Сканера» самоподписанный: добавьте CA в доверенные или выключите «Проверять TLS» (только на стенде) |
| Прогоны не импортируются | Включён ли автоимпорт у источника и `VM_POLL_ENABLED=1`; привязан ли договор; завершён ли прогон в «Сканере». Ход задач — плашка в шапке интерфейса и `docker compose logs app` |
| Повторная проверка: «не проверено: вне allowlist» | Хост не входит в allowlist договора в «Сканере» — добавьте его туда |

## 11. Запуск без Docker (разработка)

API на SQLite и dev-сервер фронтенда (с прокси `/api` на API):

```bash
cd backend
python3.12 -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt
export VM_SECRET_KEY=dev-secret-key-0123456789-abcdefgh VM_DATABASE_URL=sqlite:///./vm.db \
       VM_ENCRYPTION_KEY=$(python -c "import os,base64;print(base64.b64encode(os.urandom(32)).decode())") \
       VM_ADMIN_PASSWORD=admin-password-1 VM_DEMO=1 VM_DEMO_PASSWORD=demo-password-1
alembic upgrade head && uvicorn app.main:app --reload     # API на :8000

cd ../frontend
npm ci && npm run dev                                     # http://localhost:5174
```

Только база из Docker: `docker compose up -d db` и `VM_DATABASE_URL=postgresql+psycopg://vm:ПАРОЛЬ@127.0.0.1:15433/vm`.
