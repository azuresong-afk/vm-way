# Ручная проверка на стенде

Пошаговая проверка этапа 1 на демо-стенде: каждый шаг — что сделать и что должно получиться. Шаги идут по порядку, весь проход занимает около 30 минут. Автоматические тесты — в конце файла.

Демо-данные: проект «Демо: АО «Северный порт»», встроенный мок «Сканера» (`mock://demo`) с договором №7, 20 хостов на Debian 12 (`10.20.1.11–18`), Astra Linux SE 1.7 и РЕД ОС 7.3, три плановых прогона. В «мире» мока openssh уже обновлён на пяти Debian-хостах (`10.20.1.11–15`), хост `10.20.1.18` (mon-01) не отвечает.

## Подготовка

```bash
scripts/gen-env.sh --demo        # печатает пароли администратора и демо-пользователей
docker compose up --build -d
```

Если стенд уже поднимался, начните с чистой базы: `docker compose down -v`, затем снова `up`.

Пользователи: `admin` (пароль из `VM_ADMIN_PASSWORD`), `manager` — Руководитель, `engineer` и `engineer2` — Исполнители, `viewer` — Наблюдатель (пароль у всех четверых — `VM_DEMO_PASSWORD`).

## Шаг 1. Сборка и запуск

1. `docker compose ps`.
   **Ожидается:** `app`, `web`, `db` — `running (healthy)`. Порт 18081 открыт на всех интерфейсах, 18001 и 15433 — только на `127.0.0.1`.
2. `docker compose logs app | head -20`.
   **Ожидается:** `[preflight] настройки в порядке` (и предупреждение о демо-режиме), `применяю миграции`, `Создан первый администратор admin`, затем запросы импорта к `scanner.mock` по прогонам 100, 101, 102.
3. `scripts/smoke.sh`.
   **Ожидается:** все строки `ok`, в конце `всё в порядке`; для демо — «заявок в проекте — 14».
4. `curl -sI http://127.0.0.1:18081/ | grep -i -E 'content-security|x-frame'`.
   **Ожидается:** `Content-Security-Policy: default-src 'self'; …; frame-ancestors 'none'; …` и `X-Frame-Options: DENY`.

## Шаг 2. Проверка секретов при старте

1. В `.env` замените значение `VM_SECRET_KEY` на `CHANGE_ME`, выполните `docker compose up -d app` и через 10 секунд `docker compose logs --tail 5 app`.
   **Ожидается:** `[preflight] ОШИБКА: VM_SECRET_KEY не задан…` и `Старт остановлен`; API не запускается.
2. Верните прежнее значение и снова `docker compose up -d`.
   **Ожидается:** `app` снова `healthy`.

## Шаг 3. Вход и роли

1. Откройте `http://localhost:18081`. Войдите `admin` с неверным паролем.
   **Ожидается:** «Неверное имя пользователя или пароль».
2. Войдите `admin` с верным паролем.
   **Ожидается:** в меню Сводка, Заявки и раздел «Администрирование»: Пользователи и роли, Проекты, Источники, Журнал аудита. «Мои задачи» нет, в заявках нет кнопок «Взять», «Назначить», «Перевести» — администратор не выполняет рабочих операций.
3. «Пользователи и роли».
   **Ожидается:** `admin`, `manager` (Руководитель), `engineer`, `engineer2` (Исполнитель), `viewer` (Наблюдатель).
4. Выйдите и войдите `viewer`.
   **Ожидается:** видны Сводка и Заявки; в карточке заявки из действий только «Наблюдать» и «Копировать» у команд.

## Шаг 4. Источник и импорт

1. Войдите `admin` → «Источники».
   **Ожидается:** источник «Демо-«Сканер» (встроенный мок)», учётная запись `svc-vm`, состояние «Работает».
2. Откройте источник → «Проверить связь».
   **Ожидается:** «Вход выполнен: svc-vm, роли auditor, operator»; в «Проекты «Сканера»» договор №7 «АО «Северный порт» — аудит защищённости 2026» привязан к демо-проекту (кнопка «Снять»).
3. Войдите `manager` → «Сводка».
   **Ожидается:** импортированы три плановых прогона; плитки по уровням, график «появилось / закрыто» по неделям, среднее время устранения, последние подтверждения.
4. На «Сводке» нажмите «Импортировать новые прогоны» и дождитесь завершения задачи в плашке шапки.
   **Ожидается:** «Импорт завершён, сводка обновлена»; цифры на «Сводке» и число заявок (14) не изменились — **повторный импорт не плодит дубли**.
5. `docker compose restart app`, через минуту обновите «Заявки».
   **Ожидается:** по-прежнему 14 заявок.

## Шаг 5. Заявки сгруппированы как в «Что исправить»

1. `manager` → «Заявки», фильтр статуса — «Все статусы».
   **Ожидается:** 14 заявок. Каждая — одно действие «Что исправить» «Сканера»: пакет на ОС («Обновить openssh-server на Debian 12 до 1:9.2p1-2+deb12u3» — 8 хостов; «… на Astra Linux 1.7 …» — 6 хостов), ядро с перезагрузкой (метка «перезагрузка»), ПО («Обновить Apache Tomcat»), настройка («Настроить: Разрешены устаревшие протоколы TLS 1.0 и TLS 1.1») и «Нет исправления: tiff (Astra Linux 1.7)».
2. Статусы после трёх плановых прогонов.
   **Ожидается:** «Обновить libssl3 на Debian 12…» (6 из 6) и «Обновить sudo на Debian 12…» (8 из 8) — «Подтверждено»: третий прогон их больше не нашёл. «Обновить libexpat1 на Debian 12…» — «Регрессия»: была исправлена и снова найдена. «Нет исправления: tiff…» — «Нет исправления у производителя». Остальные — «Новая».
3. Откройте «Обновить openssh-server на Debian 12…».
   **Ожидается:** блок «Что сделать» с командой `apt-get install --only-upgrade openssh-server` и кнопкой «Копировать»; 8 хостов с установленной версией; уязвимость CVE-2024-6387 на каждом; история.
4. Фильтры: уровень «Критический», ОС «Debian 12», вид «Пакет»; поиск `CVE-2024-6387`.
   **Ожидается:** список сужается, фильтры сохраняются в адресе страницы. Ctrl+K → `10.20.1.11` находит хост и его заявки.

## Шаг 6. Назначение, статусы, комментарии

1. `manager`: отметьте две заявки со статусом «Новая» → «Назначить» → `engineer2`.
   **Ожидается:** обе — «Назначена», исполнитель — Ковалёв И. Н.
2. Отметьте заявку «Подтверждено» и «Новая» → «Перевести» → «В работе».
   **Ожидается:** «Новая» переведена; для подтверждённой — причина отказа по этой заявке, остальное выполнено.
3. Откройте назначенную заявку, оставьте комментарий.
   **Ожидается:** комментарий в «История и комментарии» с автором и временем.
4. Войдите `engineer` → «Мои задачи».
   **Ожидается:** своих заявок нет, в «Свободные заявки» — неназначенные.

## Шаг 7. Повторная проверка: исправленное закрыто, неисправленное осталось, непроверенное помечено

1. `engineer` → «Мои задачи» → «Взять» у «Обновить openssh-server на Debian 12…».
   **Ожидается:** заявка «В работе», исполнитель — Смирнов Д. В.
2. В заявке — «Исправлено — проверить». В окне все 8 хостов отмечены и отмечено «Перевести в «Исправлено, ждёт проверки»» → «Запустить проверку».
   **Ожидается:** заявка «Исправлено, ждёт проверки», в шапке плашка фоновой задачи. Через 5–10 секунд (в моке прогон завершается сразу):
   - хосты `10.20.1.11–15` — «Подтверждено»;
   - `10.20.1.16` и `10.20.1.17` — «Не подтверждено: уязвимость осталась: CVE-2024-6387»;
   - `10.20.1.18` — «Не проверено: хост недоступен: хост не ответил на пробы обнаружения» (хост **не** закрыт);
   - заявка — «Не подтверждено» (вернулась в работу), прогресс 5 из 8, системный комментарий перечисляет оставшиеся хосты;
   - в «Повторные проверки» — прогон «Проверка устранения: №… » с итогом и ссылкой на прогон «Сканера».

## Шаг 8. Журнал аудита

1. `manager` или `admin` → «Журнал аудита».
   **Ожидается:** вход и неудачный вход (с IP), создание администратора, импорт прогонов, назначение, переводы статуса (системные — от имени «система»), комментарий, запуск и итог проверки (`ticket.verify`, `ticket.verify_result`).
2. «Выгрузить CSV».
   **Ожидается:** файл CSV с теми же записями.
3. Попробуйте изменить запись журнала прямо в базе:
   `docker compose exec db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "delete from audit_log"'`.
   **Ожидается:** `ERROR: audit_log is append-only` — журнал только дополняется.

## Шаг 9. Интерфейс: темы и телефон

1. Переключите тему внизу боковой панели.
   **Ожидается:** светлая и тёмная тема, стиль как у «Сканера» (те же токены и классы), углы угловатые (`--radius: 4px`). Тема сохраняется после перезагрузки страницы.
2. Откройте «Заявки» в режиме телефона (ширина 390 px).
   **Ожидается:** строки заявок — карточками, горизонтальной прокрутки страницы нет.

## Шаг 10. Резервная копия и восстановление

1. `scripts/backup.sh backups/test`.
   **Ожидается:** `готово: backups/test (…), миграция 0001`; в каталоге `db.dump`, `manifest.txt`, `SHA256SUMS`.
2. Измените что-нибудь (комментарий к заявке), затем `scripts/restore.sh backups/test` без `--yes`.
   **Ожидается:** отказ с подсказкой про `--yes`, данные не тронуты.
3. `scripts/restore.sh backups/test --yes`, затем `scripts/smoke.sh`.
   **Ожидается:** `app` и `web` снова `healthy`, smoke зелёный, комментария из п. 2 нет, журнал аудита — как на момент копии, удалить запись из него по-прежнему нельзя.

```bash

```

## Автоматические тесты

CI (GitHub Actions, `.github/workflows/ci.yml`) на каждый PR:

- **backend** — `ruff check`, `ruff format --check`, совпадение демо-фикстуры с генератором, `pytest` (SQLite и миграции на PostgreSQL 16);
- **frontend** — ESLint, `tsc --noEmit`, vitest, сборка Vite;
- **compose** — сборка образов `app` и `web`, `docker compose up --wait` с демо-данными, `scripts/smoke.sh`, копия и восстановление, повторный smoke.

Локально:

```bash
cd backend && ruff check . && ruff format --check . && pytest -q
cd frontend && npm run lint && npm run typecheck && npm test
```
