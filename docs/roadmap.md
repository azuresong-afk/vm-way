# «Устранение» (`vm`) — архитектура и план работ

Продукт доводит каждую уязвимость, найденную «Сканером», до конца: заявка → исполнитель → исправление → **повторная проверка сканером** → закрытие с доказательством. Документ фиксирует архитектуру, модель данных, API, экраны и этапы. Решения, принятые без отдельного согласования, помечены **«Выбор:»** — их можно пересмотреть.

## 1. Архитектура

```
 браузер ──► web (nginx-unprivileged :8080, CSP, SPA)
               └── /api/* ──► app (FastAPI :8000) ──► db (PostgreSQL 16)
                                  │
                                  ├── integrations/scanner  ──► API «Сканера» (Bearer, сервисная учётка)
                                  ├── пул фоновых задач (таблица jobs, восстановление после рестарта)
                                  └── outbox событий (доставка в «Платформу» — этап 3)
```

- **Стек** — как у «Сканера»: Python 3.12, FastAPI, Pydantic 2, SQLAlchemy 2, Alembic (`0001_…`, тест-страж цепочки), PostgreSQL 16, pytest, ruff. Фронтенд: React 18 + TypeScript strict + Vite 5, react-router-dom 6, lucide-react, свой CSS на токенах, свои SVG-графики, vitest + Testing Library, ESLint 9.
- **Один origin**: nginx отдаёт SPA и проксирует `/api/*` в API с отрезанием префикса. API о префиксе не знает, поэтому в «Платформе» продукт встаёт под `/api/vm/` без изменений кода. Фронтенд берёт префиксы из `VITE_BASE` и `VITE_API_BASE`.
- **Фоновые задачи** — пул потоков в процессе API (`app/jobs.py`). Каждая задача — строка в `jobs` (`queued/running/done/failed`); при старте незавершённые задачи возвращаются в очередь. Отдельный воркер появится, когда понадобится (раскатки этапа 2 — первый кандидат).
- **Импорт** идемпотентен по `(источник, run_id «Сканера»)`, прогоны импортируются от старых к новым, незавершённые — отклоняются. Опрос просматривает последние 20 прогонов привязки и пропускает прицельные прогоны «Устранения» (их импортирует сама проверка). Источник `mock://` разрешён только на демо-стенде (`VM_DEMO=1`) и в тестах (`VM_ALLOW_MOCK_SOURCES=1`). Удалить источник с привязками или импортированными прогонами нельзя — только отключить опрос.
- **Опрос «Сканера»** — в режиме `local` раз в N минут (настройка источника) ищем новые завершённые прогоны привязанных проектов и импортируем их. В режиме `platform` вместо опроса — подписка на `scanner.run.finished` (этап 3).
- **Адаптер «Сканера»** — всё обращение к «Сканеру» в `backend/app/integrations/scanner/`: интерфейс `ScannerClient` и его реализация по HTTP. Мок `MockScanner` — это поддельный HTTP-API «Сканера» на фикстуре (3 ОС, 20 хостов), к которому ходит тот же HTTP-клиент; источник с адресом `mock://demo` работает на моке, и продукт собирается, тестируется и показывается без живого «Сканера».
- **Сверка с настоящим «Сканером».** Формы ответов сверены с кодом `azuresong-afk/scanner-way` (`scanner/api/schemas.py`, `scanner/reporting/fixplan.py`, `scanner/core/coverage.py`). Схемы переписаны в `backend/tests/scanner_contract.py`; тест прогоняет через них все ответы мока с запретом лишних полей. Что важно для продукта:
  - «Что исправить» (`GET /runs/{id}/fixes`) отдаётся страницами `{total, items}` по 500; ключ действия — `sha1(вид, (семейство, выпуск ОС), пакет вендора)[:16]`, у ядра — без пакета, у ПО — по имени продукта без ОС. Ключ меняется, когда меняется пакет вендора или вид (`package_nofix` → `package`).
  - Покрытие — `{entries: [{host, module, status, label, reason}], hosts, summary}`.
  - `POST /engagements/{id}/runs` возвращает `accepted_targets` числом и `denied_targets` списком `{target, reason, count}`; если разрешённых целей нет — 422.
  - Модулю `auth_inventory` нужны `credential_ids` («Сканер» хранит учётки сам). Прицельная проверка берёт `credential_ids` из прогона, который нашёл уязвимость.
  - Менеджер пакетов в действии — `dpkg`/`rpm`/`apk`, команды «Сканера» содержат `sudo` и для ядра — `sudo reboot`. В «Устранении» эти команды только показываются; раскатка этапа 2 строит команды сама из шаблонов.
- **Выбор: исполнитель раскаток (этап 2) — своё SSH-исполнение на `asyncssh`, а не `ansible-runner`.** Причины: (1) раскатка у нас — только из шаблонов (apt/yum/dnf/zypper/apk/ALT, ядро, перезапуск службы), декларативность Ansible не нужна; (2) нужен полный контроль над закреплением ключа хоста (TOFU и отказ при смене) и над тем, что именно выполняется — команды собираются списком аргументов из проверенных регуляркой значений, без шаблонизации Jinja и без shell-подстановки; (3) канарейка, партии, порог ошибок и аварийный стоп — наша логика, а не стратегия плейбука; (4) построчный stdout/stderr, коды возврата и длительность по каждому хосту пишутся прямо в БД; (5) образ легче и не тянет ansible-core с коллекциями. Пробный прогон — штатные «сухие» режимы менеджеров пакетов (`apt-get -s`, `dnf/yum --assumeno`, `zypper --dry-run`, `apk --simulate`).

## 2. Роли и права

| Роль | Что может |
|---|---|
| `manager` — Руководитель | всё по своим проектам: импорт, назначение, переопределение уровня с причиной, перевод статусов, повторная проверка; этап 2 — окна, правила, утверждение раскаток и исключений |
| `engineer` — Исполнитель | взять заявку, ход работ, комментарии, «Исправлено — проверить», импорт по кнопке; этап 2 — подготовка раскатки |
| `viewer` — Наблюдатель | только просмотр и отчёты |
| `admin` — Администратор | пользователи и роли, проекты (режим `local`), источники, журнал аудита; **рабочих операций не выполняет** |
| надбавка `remediate_execute` | запуск раскатки (поверх `engineer`, этап 2) |
| надбавка `custom_commands` | произвольные команды вне шаблонов (этап 2, по умолчанию ни у кого) |

Права (`Perm`) вычисляются из ролей **на каждый запрос из БД** — отзыв роли действует сразу. Каждый эндпоинт защищён `require(Perm.X)`.

**Выбор:** в режиме `local` все пользователи видят все проекты (как в «Сканере»). Ограничение по проектам приходит из токена платформы (`projects`) в режиме `platform`.

## 3. Модель данных (этап 1)

| Таблица | Назначение и ключевые поля |
|---|---|
| `users` | `username`, `display_name`, `password_hash` (scrypt; пусто для теневых записей платформы), `roles[]`, `extra_perms[]`, `platform_sub`, `is_active` |
| `projects` | контракт платформы: `id uuid`, `name`, `client`, `contract_ref`, `period_from/to`, `status`, `platform_project_id` |
| `scanner_sources` | подключение к «Сканеру»: `base_url`, `username`, `secret_enc` (AES-GCM), `verify_tls`, `poll_minutes`, `auto_import` |
| `source_links` | привязка: проект «Устранения» ↔ `engagement_id` «Сканера» |
| `scan_runs` | импортированные прогоны: `scanner_run_id`, `kind` (`scheduled`/`verification`), `status`, `finished_at`, `imported_at`, счётчики |
| `run_coverage` | покрытие прогона: `(run, host, module) → status` |
| `vulnerabilities` | зеркало находки по **`(project_id, dedup_key)`**: хост, порт, модуль, CVE/БДУ, уровень, приоритет, ПО и версия, уверенность, `state` (`open/fixed`), `first_seen/last_seen/fixed_run`, `fix_key`, `ticket_id` |
| `vulnerability_events` | история по прогонам: `appeared`, `fixed`, `regression`, `still_present` |
| `tickets` | заявка: `fix_key` (= `fixes[].key` «Сканера»), `title`, `kind`, `os`, `severity`/`priority` (+ переопределение с причиной), `status`, `assignee_id`, `is_regression`, `action` (шаги, команды по ОС, проверка, перезагрузка, пакеты, бюллетени), `evidence` (прогон-доказательство) |
| `ticket_hosts` | подзадачи по хостам: `status` (`open/confirmed/not_confirmed/unverified`), `reason`, `installed`, `last_check_run_id` |
| `ticket_watchers`, `comments`, `ticket_history` | наблюдатели, комментарии (пользовательские и системные), история изменений |
| `verifications` | повторные проверки: прицельный прогон «Сканера», статус, итог по хостам |
| `jobs` | фоновые задачи |
| `audit_log` | append-only журнал (триггер запрещает UPDATE/DELETE) |
| `outbox` | доменные события в той же транзакции (доставка — этап 3) |

**Статусы заявки:** `new` Новая → `assigned` Назначена → `in_progress` В работе → `waiting_window` Ожидает окна → `fixed` Исправлено, ждёт проверки → `verified` Подтверждено (закрыта) или `not_verified` Не подтверждено (возврат в работу). Отдельно: `risk_accepted` Принят риск, `false_positive` Ложное срабатывание, `no_vendor_fix` Нет исправления у производителя, `regression` Регрессия.

### Назначение и переходы статусов (задача 1.5)

Правила — в `backend/app/services/workflow.py`, API — в `backend/app/api/ticket_work.py`.

| Из статуса | Вручную можно перевести в | Кто |
|---|---|---|
| Новая | — (в «Назначена» — только назначением исполнителя) | |
| Назначена, Не подтверждено, Регрессия | В работе, Ожидает окна, Исправлено | исполнитель заявки или руководитель |
| В работе | Ожидает окна, Исправлено | то же |
| Ожидает окна | В работе, Исправлено | то же |
| Исправлено, ждёт проверки | В работе — **с причиной** (вернуть, не дожидаясь проверки) | то же |
| любой открытый | Принят риск, Ложное срабатывание — **с причиной** | руководитель |
| Принят риск, Ложное срабатывание | обратно — **с причиной**: в «Нет исправления», если заявка из `package_nofix`, иначе в «Назначена» или «Новая» | руководитель |
| Подтверждено | — (повторное появление открывает заявку как «Регрессия», задача 1.6) | |

- Статусы «Подтверждено», «Не подтверждено», «Регрессия», «Нет исправления у производителя» ставит **только система** (импорт и повторная проверка).
- **Взять** (`/take`) — назначить на себя свободную заявку; чужую заявку перехватывает только руководитель через `/assign`. Назначение переводит «Новая» → «Назначена», снятие исполнителя возвращает «Назначена / В работе / Ожидает окна» → «Новая». Назначить можно только активного пользователя с правом `ticket_work` (исполнитель или руководитель); на закрытой заявке назначение не меняется. `GET /users/assignable?project_id=` показывает загрузку — число открытых заявок проекта на каждом.
- **Переопределение** уровня и приоритета (`/override`) — руководитель, причина обязательна, и при установке, и при сбросе к значению «Сканера».
- **Комментарии** пишут исполнитель и руководитель; правки и удаления нет — комментарий остаётся как написан. Автор комментария, исполнитель и взявший заявку автоматически становятся наблюдателями. **Выбор:** наблюдать (`/watch`) может и роль «Наблюдатель» — подписка ничего не меняет в работе.
- **Массовые действия** (`/projects/{id}/tickets/bulk`: назначить или перевести, до 500 заявок) проверяют каждую заявку по тем же правилам: подходящие меняются, по остальным возвращается причина отказа. «В окно» — этап 2.
- **Выбор:** исключения (принятие риска, ложное срабатывание) на этапе 1 ставит руководитель с причиной; утверждающий, дата пересмотра и экран «Исключения» — задача 2.5.
- Каждое изменение — строка в истории заявки, запись в журнале аудита (`ticket.take/assign/status/override/comment/watch/bulk`) и событие в outbox (`vm.ticket.assigned/status_changed/overridden/commented`) в той же транзакции. Отказ в переходе по правам тоже пишется в журнал (`result=denied`). Заявка меняется под блокировкой строки (`SELECT … FOR UPDATE`).
- Карточка заявки (`GET /tickets/{id}`) отдаёт наблюдателей и блок `can`: в какие статусы текущий пользователь может перевести заявку и доступны ли «Взять», «Назначить», «Переопределить», «Комментировать».

### Как работает импорт и закрытие

1. Импорт прогона (`done`/`partial`/`stopped`/`interrupted`/`failed` — любой завершённый) идемпотентен по `(источник, run_id)`: повторный импорт ничего не дублирует.
2. Находки → зеркало по `dedup_key` (upsert). Ложные срабатывания «Сканера» и информационные находки в работу не берутся — «Сканер» не включает их в «Что исправить». Название заявки на пакет — «Обновить <пакет> на <ОС> до <версия>»; уровень и приоритет — из действия «Сканера» (переопределение с причиной — задача 1.5). Если «Сканер» перенёс уязвимость в другое действие, в прежней заявке остаётся системный комментарий со ссылкой. Действия «Что исправить» → заявки по `(проект, fixes[].key)`: новая заявка или дополнение существующей новыми хостами. `package_nofix` → статус «Нет исправления у производителя»; когда у такой уязвимости появляется действие с исправлением, в заявку пишется системный комментарий со ссылкой на новую заявку.
3. **Единое правило закрытия** (и для плановых, и для прицельных прогонов): уязвимость на хосте считается исправленной, только если в покрытии прогона пара `(хост, модуль)` — `completed`, а находки с этим `dedup_key` нет (или её статус `fixed`). Находка осталась — «не подтверждено». Хост не проверен (`unreachable/timeout/no_credentials/error/skipped` или пары нет в покрытии) — «не проверено» с причиной, без закрытия.
4. Хост заявки подтверждён, когда исправлены все уязвимости заявки на нём. Все хосты подтверждены → заявка «Подтверждено» с доказательством (номер, дата и ссылка на прогон). Закрытая уязвимость появилась снова → уязвимость `regression`, заявка открывается заново со статусом «Регрессия» и пометкой.
5. Повторная проверка: прицельный прогон в «Сканере» (`POST /engagements/{id}/runs`): цели — непроверенные хосты заявки, модули — те, что нашли уязвимости, `credential_ids` — из исходного прогона, имя «Проверка устранения: №N …». Фоновая задача ждёт завершения, импортирует прогон и применяет правило п. 3. Цели, отклонённые allowlist «Сканера», получают «не проверено: вне allowlist».

### Повторная проверка и автозакрытие (задача 1.6)

Правило закрытия — `backend/app/services/closure.py`, вызывается при импорте любого прогона сразу после зеркала. Прицельная проверка — `backend/app/services/verification.py`, API — `POST /tickets/{id}/verify`.

- **Что закрывает прогон.** Только пары `(хост, модуль)` из своего покрытия. Пары нет — прогон об уязвимости ничего не говорит (плановый прогон по части хостов не трогает остальные). Уязвимость, которую уже видел более поздний прогон, старым прогоном не закрывается. Прогон закрывает всё, что проверил: прицельная проверка одной заявки закрывает и исправленное в других заявках на тех же хостах.
- **Строгая и мягкая оценка хоста.** Строгая — у заявки, которую проверяют прицельно, и у заявок в статусе «Исправлено, ждёт проверки»: находка осталась → хост «не подтверждено», хост не проверен → «не проверено» с причиной из покрытия (`хост недоступен: …`, `нет учётной записи: …`). **Выбор:** у остальных заявок плановый прогон только подтверждает исправленные хосты и отмечает регрессии, а «не подтверждено / не проверено» не ставит — работа по ним ещё идёт, и такие пометки были бы шумом.
- **Итог по заявке.** Все хосты с уязвимостями подтверждены → «Подтверждено» (из любого открытого статуса, включая «Новая» и «Нет исправления у производителя») с доказательством `evidence = {номер и имя прогона, дата, вид, ссылка «{web_url}/runs/{id}»}`. «Исправлено, ждёт проверки» и есть «не подтверждено» → «Не подтверждено» (возврат в работу) с комментарием, какие хосты и что осталось. Только «не проверено» → заявка остаётся «Исправлено, ждёт проверки».
- **Регрессия.** Исправленная уязвимость снова в находках → уязвимость `open` с пометкой `is_regression`, событие `regression`; подтверждённая заявка → «Регрессия», хост — снова «открыт» с причиной. **Выбор:** заявка в работе получает только пометку и системный комментарий, статус не меняется; «Принят риск» и «Ложное срабатывание» тоже не меняются — пишется комментарий.
- **Прицельная проверка.** Цели — хосты заявки с открытыми уязвимостями (или выбранные из них). Модули — нашедшие уязвимости, плюс `discovery`, если он был в исходном прогоне: модулю `vuln` нужны найденные им порты. `credential_ids` — из прогона, который последним видел уязвимость. Хосты из разных проектов «Сканера» — по прогону на проект. **Выбор:** проверку можно запустить из любого открытого статуса; если пользователь может перевести заявку в «Исправлено», это делается автоматически («Исправлено — проверить», флажок `mark_fixed`). Пока одна проверка заявки идёт, вторую не поставить.
- **Ожидание.** Задача `verify` сохраняет номер прогона «Сканера» сразу после запуска, затем опрашивает его раз в `VM_VERIFY_POLL_SECONDS` (5 с) до `VM_VERIFY_TIMEOUT_MINUTES` (240 мин). После рестарта задача продолжает ждать тот же прогон, второй не запускается. Пока прогон идёт, задача занимает один поток пула.
- **Итог проверки** (`verifications.result`): по каждому хосту — статус и причина; `outcome` — `verified`, `not_verified`, `partial` (часть подтверждена, остальное не проверено) или `unverified`. Ни одной цели в allowlist → «Сканер» отвечает 422, прогона нет, все хосты «не проверено: вне allowlist».
- Системные переводы статуса пишутся в историю, в журнал аудита от имени «система» (`ticket.status`) и событием `vm.ticket.status_changed`. Запуск и итог проверки — `ticket.verify` и `ticket.verify_result`. Итог — событие `vm.remediation.verified {ticket_id, run_id, result}`.

## 4. API (этап 1)

Все списки — `limit/offset`, всего — `X-Total-Count`. Все изменения — запись в журнал аудита.

| Метод и путь | Право |

### Интерфейс (задача 1.7)

Код — `frontend/` (React 18 + TypeScript strict + Vite 5, без UI-библиотек). Стили — копия `styles.css` «Сканера» с теми же классами; дополнения «Устранения» — в конце файла, только на токенах.

- **Выбор: угловатый вариант** (решение Антона): `--radius: 4px`, `--radius-sm: 2px`. Все скругления в стилях, включая модальное окно (у «Сканера» оно фиксированные 14 px), статусные пилюли и чипы, выражены через эти два токена — вариант «Сканера» включается заменой двух строк. Круглыми остаются только точки, аватар и спиннер.
- Экраны: Вход, Сводка, Заявки (фильтры в адресе, сортировка, массовые «Назначить» и «Перевести» с причинами отказа по каждой заявке, шторка), Заявка (что сделать с «Копировать», хосты, уязвимости, проверки, история и комментарии, действия по блоку `can`), Мои задачи (свои и свободные заявки), Администрирование (Пользователи и роли, Проекты, Источники с проверкой связи и привязками, Журнал аудита с выгрузкой CSV). Ctrl+K — заявки по номеру и названию, хосты, CVE и БДУ, переходы по разделам; плашка фоновых задач в шапке.
- **Сводка** (`GET /projects/{id}/summary`): **Выбор:** недели «появилось / закрыто» и среднее время устранения считаются по уязвимостям (`first_seen_at` — дата нашедшего прогона, `fixed_at` — дата подтвердившего), а не по заявкам — заявка объединяет уязвимости, найденные в разное время. «Изменение за период» — открытые сейчас минус открытые на начало периода. На графике новые уязвимости — вверх от оси, закрытые — вниз, у графика есть вариант «Таблица».

### Развёртывание (задача 1.8)

Стек — `docker-compose.yml` в корне: `app` (API :8000, порт хоста `VM_API_PORT` 18001 только на `127.0.0.1`), `web` (nginx-unprivileged :8080, порт хоста `VM_WEB_PORT` 18081), `db` (postgres:16, `VM_DB_PORT` 15433 только на `127.0.0.1`, том `vm_pg_data`). Ротация логов, `restart: unless-stopped`. Подробно — `docs/INSTALL.md`.

- **Старт `app`** (`backend/docker/entrypoint.sh`): `python -m app.preflight` → `alembic upgrade head` с повторами, пока БД не ответит → uvicorn в один процесс (фоновые задачи — пул потоков внутри). Первого администратора и демо создаёт приложение при старте. Процесс без root (uid 10001).
- **Проверка секретов** (`app/preflight.py`): пустые, `CHANGE_ME` или слабые `VM_SECRET_KEY` (< 32 символов), `VM_ENCRYPTION_KEY` (не 32 байта base64), пароли администратора и демо (< 10 символов) останавливают старт с причиной в логе; `VM_AUTH_MODE=platform` до этапа 3 тоже. **Выбор:** проверка всегда строгая, без отдельного режима production: для разработки без Docker она не вызывается.
- **Готовность** `/health/ready`: БД доступна **и** схема на последней миграции (как у «Сканера»); на этом стоит healthcheck образа, `web` ждёт `app: service_healthy`.
- **Адрес БД** для `app` собирается в compose из `POSTGRES_USER/PASSWORD/DB` — пароль задаётся один раз. **Выбор:** `.env` обязателен (`scripts/gen-env.sh` создаёт его со случайными секретами), значений по умолчанию для секретов нет.
- **web** (`frontend/Dockerfile`, `frontend/nginx.conf.template`): сборка Vite на node:22-alpine, раздача nginx-unprivileged; `/api/*` → `API_UPSTREAM` с отрезанием префикса; CSP и заголовки — один в один со «Сканером». `VITE_BASE` / `VITE_API_BASE` — аргументы сборки.
- **Резервные копии**: `scripts/backup.sh` (pg_dump custom + манифест + SHA256), `scripts/restore.sh КАТАЛОГ --yes` (останавливает app и web, пересоздаёт базу, загружает дамп, миграции догоняются при старте). `.env` в копию не входит.
- **CI**: job `compose` собирает образы, поднимает стек с демо (`up --wait`), гоняет `scripts/smoke.sh`, копию и восстановление.

## 7. Вопросы, которые меняют решение

1. ~~Доступ к коду «Сканера»~~ — снят: адаптер и фикстура сверены с репозиторием `scanner-way` (см. раздел 1).
2. **Видимость проектов в режиме `local`.** В «Сканере» нет участников проекта: доступ определяется только ролью. **Выбор:** делаем так же, все пользователи видят все проекты. Ограничение по проектам приходит из токена платформы (`projects`) в режиме `platform`. Если ограничение нужно раньше, добавлю таблицу участников.
3. **Ложное срабатывание обратно в «Сканер».** В «Сканере» разметка (`PUT /findings/{id}/false-positive`) требует права `triage_findings`, а оно есть у роли `operator`. Эта роль сервисной учётке всё равно нужна для прицельных проверок, поэтому **выбор:** синхронизация будет на этапе 2, по флажку в настройках источника и выключена по умолчанию.

Остальное выбрано самостоятельно и отмечено «Выбор:» выше.
