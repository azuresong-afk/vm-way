# «Устранение» — управление уязвимостями и обновлениями

Третий продукт семейства «Сканер» / «Устранение» / «Аттестация». «Устранение» доводит каждую уязвимость, найденную «Сканером», до конца: заявка → исполнитель → исправление → **повторная проверка сканером** → закрытие с доказательством. Работает только с системами заказчика в рамках договора.

Архитектура, модель данных, API и план по задачам — в [docs/roadmap.md](docs/roadmap.md).

## Быстрый старт (Docker)

Нужны Docker Engine 24+ с Compose v2 и `openssl`.

```bash
scripts/gen-env.sh                # .env со случайными секретами, печатает пароль администратора
docker compose up --build -d      # app (API), web (nginx), db (PostgreSQL 16)
scripts/smoke.sh                  # проверка стека через веб
```

Интерфейс — `http://localhost:18081`, вход — администратор из `.env`. Порты меняются в `.env` (`VM_WEB_PORT`, `VM_API_PORT`, `VM_DB_PORT`); API и БД слушают только `127.0.0.1`.

Демо-стенд без настоящего «Сканера» (встроенный мок: 3 ОС, 20 хостов, три плановых прогона; пользователи `manager`, `ciso`, `engineer`, `engineer2`, `viewer`):

```bash
scripts/gen-env.sh --demo && docker compose up --build -d
```

## Возможности

- Импорт прогонов «Сканера» вручную и по расписанию опроса. Находки объединяются в заявки с подзадачами по хостам, исполнителями, комментариями и историей.
- Активы, группы и правила назначения помогают распределить заявки. Для работ на хостах задаются окна обслуживания и периоды запрета изменений.
- Раскатка по SSH включает пробный прогон, согласование другим сотрудником, обновление контрольного хоста и последующих партий. По каждому хосту сохраняются журнал и версии до и после обновления.
- Для принятого риска и ложных срабатываний предусмотрены исключения. Отчёт о ходе устранения доступен в HTML, PDF, DOCX и JSON.

### Как подтверждается исправление

После раскатки система запрашивает повторную проверку успешно обновлённых хостов. Проверку можно также запросить из заявки. Для планового и прицельного прогона действует одно правило: результат учитывается для конкретной пары «хост и модуль». Если модуль завершил проверку и находка исчезла или получила статус `fixed`, исправление подтверждается. При недоступности хоста или ошибке проверки заявка остаётся открытой.

Заявка получает статус «Подтверждено», когда подтверждены все её хосты. Повторное появление закрытой находки открывает заявку со статусом «Регрессия».

Реализованные этапы и планы развития приведены в [дорожной карте](docs/roadmap.md#6-этапы).

## Разработка

Бэкенд (Python 3.12):

```bash
cd backend
python3.12 -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt
ruff check . && ruff format --check . && pytest -q
# Все тесты на PostgreSQL (необязательно; так же идёт CI). Нужна отдельная пустая база:
# схема public в ней пересоздаётся перед каждым тестом.
VM_TEST_ON_PG=1 VM_TEST_PG_URL=postgresql+psycopg://vm:vm@127.0.0.1:5432/vm_test pytest -q
```

Демо-фикстура «Сканера» генерируется скриптом и проверяется в CI на совпадение:

```bash
python -m app.integrations.scanner.fixtures.generate > app/integrations/scanner/fixtures/demo.json
```

Фронтенд (Node 22):

```bash
cd frontend
npm ci
npm run lint && npm run typecheck && npm test
npm run dev   # http://localhost:5174, /api проксируется на API :8000 (VM_API_URL)
```

Запуск API без Docker — [docs/INSTALL.md, раздел 11](docs/INSTALL.md#11-запуск-без-docker-разработка). CI (`.github/workflows/ci.yml`): ruff, pytest с миграциями на PostgreSQL, ESLint, typecheck, vitest, сборка, а также сборка образов, проверка всего стека `docker compose up` и сквозной тест интерфейса на Playwright (`e2e/`, см. [docs/TESTING.md](docs/TESTING.md#сквозной-тест-интерфейса)).

Аудит зависимостей (`.github/workflows/audit.yml`, на PR, в main и раз в неделю): `pip-audit` по закреплённым версиям и `npm audit` по зависимостям сборки; обновления предлагает Dependabot (`.github/dependabot.yml`).
